# 我用一根数据线让手机自己投简历：BOSS直聘自动投递脚本的工程实现

> 不是"AI 帮你写简历"，也不是"一键海投神器"。就是一个把「翻岗位、读 JD、判断我干不干得了、发第一句话」这套动作自动化的脚本。代码已开源，附踩坑记录。

---

## 一、起因

秋招投到第 100 份的时候，我发现自己每天有一半时间在做同一件事：

1. 在信息流里刷岗位，看标题点进去
2. 读一遍 JD，判断「这个我能不能干」
3. 觉得能，点「立即沟通」
4. 发一段自我介绍

第 3 步和第 4 步是纯体力活。第 2 步需要判断，但判断标准其实很稳定 —— 我的技术栈就那么些，JD 里有没有，一眼就能看出来。

所以我想要的不是"更聪明的 AI 帮我写话术"，而是**把第 1-4 步的机械部分自动化，把判断标准写成代码**。

---

## 二、为什么不用现成方案

试过三条路，都放弃了：

**① 网页版 + Playwright**
BOSS 的网页版能看到的信息比 App 少一大截，沟通入口也基本只在 App 里。而且网页端的风控对无头浏览器很不友好。

**② Appium**
功能上完全够用，但它的定位是"跨平台测试框架"，启动一个 session 要十几秒，跑一轮几百次点击，光启动开销就受不了。

**③ 各种 RPA 工具**
录制回放那套，界面一改版全废，而且没法写条件判断。

最后选了 **ADB + [uiautomator2](https://github.com/openatx/uiautomator2)**：

- 直接操作真机，看到的东西和用户手点完全一致
- 不需要 root、不需要 hook、不需要改包
- Python 直接调，写判断逻辑没有中间层
- 每一步都能 dump 出 XML，出问题可以精确知道当时屏幕上是什么

代价是必须有手机、必须有线，速度也比接口慢（实测每投一个 6–10 秒）。

## 三、整体流程

```
读取台账（已投过的公司 → 跳过）
  ↓
等设备 → 体检 → 回到「职位」列表（不预查额度，直接开投）
  └─ 逐张卡片：
       打开详情
       ├─ 按钮不是「立即沟通」→ 已联系过，返回
       ├─ 胜任度判断不通过    → 返回（不打扰对方）
       └─ 通过 → 点「立即沟通」
                 ├─ 弹「今日还能沟通 N 次」→ 点掉「好」，继续
                 └─ 弹「已达上限」        → 停
                 App 自动发默认招呼语（这一步就消耗 1 次额度）
                 输入该类别话术 → 点最右侧发送键
                 校验气泡出现 → 返回列表
                 写台账
```

停止条件：App 提示「已达上限」/ 连续 4 次失败 / 列表翻到底。

这里有个坑值得单独说：沟通到 120 次左右，点「立即沟通」会弹「今日还能沟通 30 次」。
我第一版脚本遇到弹窗就按返回键 —— 弹窗关掉 → 再点沟通 → 又弹 → 又返回，
直接死循环，得我自己伸手点一下「好」它才继续。
后来改成**识别弹窗上的确认按钮直接点掉**，再重新点沟通，就顺了。
判断「是不是真没额度」也有讲究：不能看到「上限」就停，
因为「已达 120 次」这句里也有「已达」，会误判。

## 四、最难的不是点击，是"判断我干得了吗"

这是整个项目里改了最多遍的地方，也是我觉得最有意思的部分。

### 4.1 第一版：按薪资筛

一开始想得很简单：我期望 10–40K，那就把区间外的过滤掉。

结果发现招聘软件上的薪资是**随手写的**。同一个岗位写「15-30K」，另一个几乎一样的写「面议」，还有个写「8-15K」但聊下来能给到 20。用薪资当硬门槛，纯粹在漏机会。

后来干脆全放开：**学历、经验年限、薪资，一个都不筛。**

列表卡片只判断一件事 —— 这个岗位还在招吗（带「停止招聘/已关闭」才跳过）。

### 4.2 第二版：进详情页读 JD 再判断

卡片上没有 JD，所以真正的判断要放到打开详情之后。

逻辑是：岗位名先过一遍黑名单（销售、客服、运营、产品经理……），
是技术岗就检查 JD 里有没有我会的技术词，一个都没有就跳过。

技术词清单是个带权重的字典：

```yaml
skills:
  langchain: 3     # 3 = 核心，能聊实现细节
  rag: 3
  python: 3
  fastapi: 3
  docker: 2        # 2 = 熟练
  redis: 1         # 1 = 了解
```

**关键点：这份清单只写我真会的。** 写进去一个不会的，脚本就会替我投一个我干不了的岗位，浪费额度还尴尬。

### 4.3 第三版：信息不足，不判死

上线后我发现漏投了一批岗位，其中最典型的一个：岗位名是 **「线上面试（离职优先）」**，薪资 25-40K，公司是做芯片的。

按技术词匹配，它一个词都没命中 —— 因为 JD 只有 149 个字，写的是"负责公司 AI 相关产品研发，本科以上，双休，五险一金"。

但这是个正经岗位，我该投。

问题出在我的规则把「匹配不到」当成了「不匹配」。这两件事完全不同：

- 不匹配 = 我看了 JD，里面要的是 C++ 和嵌入式
- 匹配不到 = JD 太短/太潦草，我根本没有信息做判断

于是加了第三条分支：

```
标题看不出是什么岗（这类钩子标题）
    ├─ JD 技术权重够        → 投
    ├─ JD 写了门店/提成/销售指标 → 跳过（其实是销售岗）
    └─ JD 短到没信息可判断   → 投（信息不足不判死）
```

最后一条是踩坑换来的。BOSS 上大量真实岗位用「线上面试（离职优先）」「急招！双休」当标题，JD 就一两句话。纯靠关键词匹配，会系统性地漏掉这一整类。

## 五、话术：为什么是固定模板，而不是让 AI 现写

很多人第一反应是"接个大模型，每个岗位生成一段定制话术"。

我试过，放弃了，原因是三个：

**① 质量会飘。** 同样的简历，今天生成得很具体，明天生成得很空。发出去的话术质量不稳定，等于把第一印象交给随机数。

**② 会编。** 模型很容易"顺着 JD 编经历"——JD 里写了 Milvus，它就说你用过 Milvus。这种话说出去，面试三分钟就露馅。

**③ 改不动。** 话术要迭代，得改代码；固定模板的话，改一个 yaml 文件就行。

所以最终方案是：**按 JD 关键词把岗位归成 5 类，每类一条提前写好、人工确认过的话术**，长度控制在 80 字以内，不替换岗位名（一填就超字数）。

归类规则很简单：岗位名 + JD 正文匹配关键词，岗位名命中权重 ×3。

```yaml
messages:
  rag:   "我之前做过保险条款的RAG问答，从文档切片、向量加BM25混合检索，到答不准就拒答，这几块都是我写的。您这岗位也是这个方向吗？"
  agent: "我做过维保调度的Agent，用ReAct做工具编排，参数校验和防编造护栏都是自己加的，线上跑过。您这边Agent主要落在哪块业务？"
  eng:   "我主要写Python后端，FastAPI异步这块比较熟，采集用asyncio做过限流，Docker部署也是自己弄的。您这边后端用什么栈？"
```

写法上有个小心得：**口语化地说清「我做过什么、怎么做的」，最后落一句具体的话头**。

- 「做过 RAG 项目」→ 没人信，人人都这么写
- 「从文档切片、向量加 BM25 混合检索，到答不准就拒答」→ 同行一眼知道你真做过
- 「我主要写 Python 后端，Docker 部署也是自己弄的」→ 比「精通 Docker」可信
- 结尾**别写「可聊」**，太轻浮，像约人闲聊。技术岗反问一句（您这边主要落在哪块业务？），对面是技术负责人，愿意聊细节；通用岗直接说「合适的话我把简历发您」，HR 每天看几十条，省掉他一个决策

## 六、踩过的坑（这部分可能比正文有用）

**① 发送按钮没有 resource-id，emoji 按钮离输入框更近**

输入框那一行是 `[语音] [EditText] [表情] [发送]`。我一开始取的是「输入框右边第一个可点控件」——点到了表情按钮，表情面板弹出来，消息没发出去，脚本还以为发出去了，返回列表留下一条草稿。

正确做法是取**这一行最右边**的控件。

**② 发送必须校验，不能假设成功**

现在每次发送后都会去聊天记录里找刚发的那条气泡（`tv_content_text`）。找不到就关掉表情面板重试，最多 3 次，放弃前一定清空草稿，不留半截话。

**③ uiautomator2 的 server 会被连续滑动搞崩**

快速刷列表时，背后的 `app_process` 服务会掉线。解法是所有滑动 `duration ≥ 0.35` 并且滑完 sleep，再包一层重试 + 重连。

**④ 误触会跳第三方 App**

有一次点到了支付宝的广告，整个流程跑到别人 App 里去了。现在每处理一个岗位前都会重新确认前台包名，不对就拉回来。

**⑤ 学历、经验、薪资别当门槛**

前面说过了，再强调一次：这三个字段在招聘软件上基本不可信。

**⑥ 分辨率是写死的**

所有坐标都是在 1440×3200 上标定的。开源前加了层等比缩放（`tap/swipe` 里按实际分辨率换算），换手机不用改调用代码，但 UI 结构变了还是得改选择器。

## 七、结果

- 台账累计 **110 条成功投递**，全部去重，同一家公司不会重复打扰
- 每投一个 6–10 秒（不模拟人手，全速跑），一次跑满额度大概 20–25 分钟
- 中途 Ctrl+C 随时停，重跑从断点继续
- 命中断点条件（额度上限/连续失败）会自己停，不会硬烧额度

回复率我没做统计 —— 那个数据得自己看聊天列表，而且受岗位质量影响太大，写出来容易误导。

## 八、关于隐私：这个脚本别人怎么用

这是开源前想得最多的一件事。

原版里我的技能清单、话术、简历细节全是硬编码在代码里的。这意味着两件事：**别人拿去用不了**，而且**一开源就把我的隐私公开了**。

所以做了一次彻底改造：所有个人化的东西抽到 `config/profile.yaml`，代码里零硬编码。

```
config/
├── profile.example.yaml   # 通用模板（入库）
└── profile.yaml           # 你的技能/话术/路径（.gitignore）
```

配套写了个 `onboard.py`，别人的使用路径是：

```bash
python scripts/onboard.py --resume 我的简历.pdf --city 北京
```

它会读简历（PDF/DOCX/TXT）→ 抽出你真会的技术词 → 生成配置草稿 →
打印几段可以当话术素材的项目描述。

然后人工过一遍：删掉不会的技术，把话术草稿换成自己真做过的项目。

```bash
python scripts/onboard.py --check   # 校验：话术超长、技能为空都会报错
```

台账、日志、简历原文、`profile.yaml` 全部在 `.gitignore` 里。
仓库里只有代码和通用模板，没有任何人的简历或聊天记录。

## 九、合规与风险

说清楚比较好：

- 这个脚本是**给自己账号用的效率工具**，不是刷量机器
- 它不抓取、不存储招聘方数据，只在本地记「我投过谁」
- 不自动回复聊天 —— 聊天是转化率最高的一环，值得自己回
- 命中「今日上限 / 操作频繁」立刻停
- **任何自动化都有账号风险**，用不用、怎么用，自己判断

## 十、最后

做完这个项目最大的感受不是"自动化真爽"，而是：

**把判断标准写成代码的过程，逼着我把"我到底会什么"想清楚了。**

以前投简历是感觉驱动——"这个看起来能投"。写成 `skills` 字典之后，我得一条条确认：这个技术我是"能聊实现细节"，还是"只知道名字"？写错权重，脚本就会替我投错岗位。

那 70 个技术词的权重，比任何一份自我介绍都更接近真实的我。
